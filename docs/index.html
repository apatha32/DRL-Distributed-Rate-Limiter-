Overview

What DRL Does

DRL sits between your clients and downstream services, intercepting every request and deciding in real time whether to allow or block it based on configurable per-client policies.

Client
Any HTTP caller
FastAPI Service
POST /v1/check
RL Agent

Redis
State store
Decision
200 allow / 429 block

Consistent Across Nodes

Every decision is one atomic Redis Lua script that uses the Redis clock, so any number of API instances share the same counters and can never both spend a client's last unit of quota. A test runs 8 concurrent nodes and checks that exactly the limit is admitted.

Circuit Breaker Protection

A circuit breaker wraps every Redis call. After repeated failures it opens, and the service either fails open (requests allowed and marked X-RateLimit-Degraded) or fails closed with 503, depending on FAIL_MODE.

Full Observability

Prometheus metrics at /metrics cover decisions, latency histograms, Redis errors, and AI token usage. OpenTelemetry traces export over OTLP to Jaeger or any compatible backend.

Per-Client Policy Engine

Rules are set per client and per endpoint (for example a stricter limit on /login) and can be changed at runtime through the API-key protected admin API, without a restart.

Correlation ID Tracking

Every request gets a correlation ID that is attached to its log lines and returned in the X-Correlation-ID header, so one request can be followed through the logs.

AI Adaptive Limits

Every 10 seconds a Q-learning agent reviews each client's traffic level, block ratio and trend, and raises, holds, or lowers its limit by 10%, learning from the reward each change earns.

Core Algorithms

Four Rate Limiting Strategies

Each algorithm is a single Redis Lua script: the read, decision and write happen atomically in one round trip, using the Redis server clock, so limits hold across any number of limiter nodes. Choose one via the ALGORITHM environment variable.

Algorithm Behavior Burst Tolerance Redis Keys p50 Latency
Token Bucket Tokens refill continuously at a fixed rate. Each request consumes one or more tokens. Unused tokens accumulate up to the bucket capacity. High. Accumulated tokens permit temporary spikes. 1 hash per client 0.10ms
Leaky Bucket Each request adds water to a bucket that drains at a constant rate. Requests that would overflow it are rejected, enforcing a smooth outflow. Bounded. Up to the bucket size, then a steady rate. 1 hash per client 0.10ms
Fixed Window Time is divided into discrete windows. A counter increments per request and resets at the window boundary. Moderate. Double-rate bursts are possible at boundaries. 1 hash per client 0.10ms
Sliding Window Keeps a sorted-set log of request timestamps and counts those inside a true rolling window. Eliminates the boundary spike problem. Low. Accurate continuous enforcement. 1 sorted set per client 0.10ms
Reinforcement Learning

Adaptive Limits with Q-Learning

Each client, and each endpoint rule, gets its own Q-table. Every 10 seconds the agent looks at the last window, updates the Q-table from the reward, and picks its next action. It starts out exploring at random and relies more on what it has learned as exploration decays. Reading the current limit on the request path is a memory lookup; learning happens in the background.

Claude

AI Traffic Analyst

On request, Claude reviews a snapshot of the limiter and the RL agent's recent decisions, explains what is happening in plain English, flags suspicious clients, and proposes rule changes. Nothing changes until an admin applies a recommendation, and Claude is never on the request path, so it adds no latency to any decision.

Quickstart

Run It Yourself

The live website needs nothing installed. To run everything on your own machine you need Docker and Node.js 20 or newer. 

# Clone the repository
git clone https://github.com/apatha32/DRL-Distributed-Rate-Limiter-.git
cd DRL-Distributed-Rate-Limiter-

# Start Redis and the API (bound to localhost only)
docker network create drl
docker run -d --name drl-redis --network drl redis:7-alpine
docker build -t drl-api .
docker run -d --name drl-api --network drl -p 127.0.0.1:8000:8000 \
  -e REDIS_URL=redis://drl-redis:6379/0 \
  -e ADMIN_API_KEY=dev-admin-key \
  drl-api

# Start the dashboard, then open http://localhost:5173 and click Run live demo
cd dashboard && npm install && npm run dev

# Or from a terminal: 60 requests for client_b (limit 50 per minute)
for i in $(seq 60); do
  curl -s -o /dev/null -w "%{http_code}\n" -X POST http://localhost:8000/v1/check \
    -H "Content-Type: application/json" -d '{"client_id": "client_b"}'
done | sort | uniq -c
#   50 200
#   10 429
