Overview

What DRL Does

DRL sits between your clients and downstream services, intercepting every request and deciding in real time whether to allow or block it based on configurable per-client policies.

Stateless Horizontal Scaling

The API service holds no local state. All rate limit counters and token buckets live in Redis, so any number of instances can run behind a load balancer and reach consistent decisions.

Circuit Breaker Protection

A circuit breaker wraps every Redis call. When failure thresholds are breached the service enters open mode and either fails open or closed based on your configured fail strategy.

Full Observability

Prometheus metrics expose request counters, latency histograms, and error rates. OpenTelemetry spans and Jaeger distributed tracing provide end-to-end request visibility.

Per-Client Policy Engine

Rate limit rules are stored per client ID and per endpoint. Rules are configurable at runtime via the admin API without requiring a restart or redeployment.

Correlation ID Tracking

Every request receives a unique correlation ID that is propagated through all log entries, trace spans, and response headers, enabling precise debugging across distributed components.

AI Adaptive Limits

A Q-learning agent observes each client's traffic patterns and continuously adjusts rate limits upward or downward in response, maximizing throughput while protecting against abuse.

Core Algorithms

Three Rate Limiting Strategies

Each algorithm is a self-contained Redis-backed implementation. Choose one via the ALGORITHM environment variable or switch at runtime.

Algorithm Behavior Burst Tolerance Redis Keys p50 Latency
Token Bucket Tokens refill continuously at a fixed rate. Each request consumes one or more tokens. Unused tokens accumulate up to the bucket capacity. High. Accumulated tokens permit temporary spikes. 2 per client 1.2ms
Fixed Window Time is divided into discrete windows. A counter increments per request and resets at the window boundary. Moderate. Double-rate bursts are possible at boundaries. 1 per client 0.8ms
Sliding Window Evaluates requests within a true rolling window using per-second sub-buckets. Eliminates the boundary spike problem. Low to moderate. Accurate continuous enforcement. N per client (N = window seconds) 2.3ms
Reinforcement Learning

Adaptive AI Rate Limiting

DRL includes a Q-learning agent that replaces static rate limits with dynamically adjusted ones. Each client gets an independent Q-table. The agent explores policy space and converges on limits that maximize throughput while minimizing abuse signals.

State Space

Traffic level low / medium / high
Block ratio low / medium / high
Traffic trend falling / stable / rising
Total states 27

Actions and Reward

Action 0 Decrease limit 10%
Action 1 Keep current limit
Action 2 Increase limit 10%
Reward signal +allowed, -0.5 blocked

Learning Parameters

Learning rate 0.1 (RL_LEARNING_RATE)
Discount factor 0.9 (RL_DISCOUNT_FACTOR)
Epsilon start 1.0, decays to 0.05
Update interval 10s (RL_UPDATE_INTERVAL_SEC)

Quickstart

Up in 60 Seconds

The full stack (API, Redis, PostgreSQL, Jaeger, Prometheus) starts with a single command. 

# Clone the repository
git clone https://github.com/apatha32/DRL-Distributed-Rate-Limiter-.git
cd DRL-Distributed-Rate-Limiter-

# Start the full stack
docker-compose up --build

# Check a rate limit (allow)
curl -X POST http://localhost:8000/v1/check \
  -H "Content-Type: application/json" \
  -d '{"client_id": "demo", "limit_key": "api", "cost": 1}'

# Enable the RL adaptive agent
ENABLE_RL=true docker-compose up --build

# Inspect RL diagnostics for a client
curl http://localhost:8000/v1/rl/diagnostics/demo
